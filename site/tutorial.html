Codelab · 6 chapters · 2–3 hours

Writing a journal that survives power cuts on QNX 8.0, and proving it

You build a small automotive event data recorder — a "black box" — whose journal is a raw partition on QNX 8.0, and you prove that it comes back with the data it had already promised to keep. The proof is not a story: it is an exhaustive enumeration of every disk state a power cut can leave behind, checked against the data that was injected. Written for a developer who knows C and has never written a crash-tolerant log. At the end you have a journal you can read, a test suite you can re-run, and a claim that is a count.

1 · The block format and CRC-32C

The problem. You call write() and the power dies. The medium may have kept all 512 bytes, none of them, or the first 300 — and a half-written sector does not look half-written. So the first piece of the journal is not a buffer or a queue: it is a unit of storage you can judge.

The idea. One 512-byte sector with a 48-byte header (magic, version, sequence number, session id, type, length) and two checksums: payload_crc over the body, block_crc over header plus body. A block whose CRC is invalid is never returned as data, and a record is valid only if every one of its chunks is valid — half an event is worse than no event.

Files. fmt/ambre_crc32c.c, fmt/ambre_fmt_block.c, fmt/ambre_types.h; the proofs live in tests/test_crc32c.c and tests/test_block.c.

    for (i = 0; i < len; i++) {
        c = s_crc32c_table[(c ^ p[i]) & 0xFFu] ^ (c >> 8);
    }
    return c ^ 0xFFFFFFFFu;

Prove it. make && ./build/test_crc32c && ./build/test_block → PASSED: 85 checks, 0 failures and PASSED: 118 checks, 0 failures. Watch crc32c_check_value produce the public constant 0xE3069283, and block_corruption_error_codes return a different error for a bad magic, a bad version and a bad CRC.

Requirement covered. STO-02 REP-05 — Read the chapter (01-block-and-crc.md)

2 · The table in two copies

The problem. The allocation table says where the data is, and it changes on every event — so it is the structure most likely to be caught mid-write by the cut. Lose the table and the data is still physically on the medium but unreachable, which from the driver's point of view is indistinguishable from data loss.

The idea. Keep the table in two copies, each with a generation counter and a CRC. The writer always overwrites the copy with the lower generation; the reader always trusts the copy with the highest valid generation. Those two rules are what make a single-copy update safe: at every instant one copy is intact and carries the newest committed generation.

Files. fmt/ambre_fmt_table.c; the proofs live in tests/test_table.c and tests/test_scan.c.

    /* STO-04: always overwrite the OLDER copy; an invalid copy counts as
     * older than any valid one. Both invalid -> fall back to copy A. */
    if (p.valid_a && p.valid_b) {
        target = (p.a.generation <= p.b.generation)
                 ? AMBRE_TABLE_A_OFFSET : AMBRE_TABLE_B_OFFSET;

Prove it. ./build/test_table && ./build/test_scan → PASSED: 44 checks, 0 failures and PASSED: 68 checks, 0 failures. Watch table_commit_alternates_corrupt (corrupt the copy just written: the other one still works) and scan_rebuild_table_exact_events (with the table gone, the rebuild finds exactly the injected events and nothing else).

Requirement covered. STO-03 STO-04 REP-02 — Read the chapter (02-table-two-copies.md)

3 · The continuous journal

The problem. A crash is short, but around it the car is doing 90 km/h and the interesting data is produced continuously, long before anyone knows an event will happen. The journal cannot be an event log: it must be always on, appending bands of samples at a fixed cadence, on a medium with no file system in the way.

The idea. Build the journal on a vtable of four operations — read, write, flush, mark — and a simulated disk that logs every operation in order. That log is the ground truth: for any cut point it says exactly what was durable. Each record is staged into a pre-allocated buffer and submitted as one contiguous write, and a record never straddles two segments.

Files. fmt/ambre_journal_core.c, fmt/ambre_fmt_scan.c, host/simdisk/; the proofs live in tests/test_simdisk.c, tests/test_scan.c and tests/test_journal.c.

    /* One single contiguous write: that is what GEL-01 asks for. */
    rc = j->disk->write(j->disk->ctx, ambre_journal_write_offset(j), j->rec_buf,
                        (size_t)chunks * AMBRE_BLOCK_SIZE);

Prove it. ./build/test_simdisk && ./build/test_scan && ./build/test_journal → PASSED: 3345 checks, 0 failures, PASSED: 68 checks, 0 failures and PASSED: 4195 checks, 0 failures. Watch logging_exactness (the log records exactly the calls made, in order) and locked_event_is_never_recycled (a locked event is never a victim).

Requirement covered. ACQ-06 STO-01 STO-03 — Read the chapter (03-continuous-journal.md)

4 · The critical path of the freeze

The problem. The event you must record is the event that destroys your power supply. From the impact to the loss of the 12 V rail there are tens of milliseconds, and about a kilobyte of Class A data must be durable — not merely buffered — inside that window.

The idea. Three steps and no more: one contiguous write of the emergency record, one allocation-table commit, one flush. "Acquired" means the flush was acknowledged, never that write() returned. The path allocates nothing, faults nothing and waits on no lower-priority process — the emergency snapshot is staged into the journal's own pre-allocated buffer.

Files. fmt/ambre_journal_event.c; the proofs live in tests/test_journal.c (trigger_path_is_write_commit_flush) and tests/test_explore.c (explore_acquisition_boundary).

    /* GEL-01: the class A snapshot leaves in ONE contiguous write. */
    rc = ambre_journal_write_record(j, (uint8_t)AMBRE_REC_EMERG,
                                    emerg->t0_ts_us, emerg,
                                    (uint32_t)sizeof(*emerg), &seq, &blocks);
    /* GEL-02: table update, then the flush that makes the event acquired. */
    rc = ambre_journal_register_event(j, &desc);

Prove it. ./build/test_journal && ./build/test_explore → PASSED: 4195 checks, 0 failures and PASSED: 58 checks, 0 failures. The trace of a trigger must be exactly one EMERG write, one table commit, one flush — in that order. If a refactor ever adds a fourth operation, this test says so.

Requirement covered. GEL-01 GEL-02 GEL-03 — Read the chapter (04-freeze-critical-path.md)

5 · Idempotent recovery

The problem. Recovery is the code that runs after the failure it is supposed to handle, so it will be interrupted by exactly the event it is recovering from — and then run again. It must be safe on anything (a half-written record, a wiped table, a partition of noise) and idempotent: run it twice, or after being interrupted, and the final state must be the same.

The idea. Keep the valid table copy with the highest generation, else rebuild the map by scanning; drop torn records; register an EMERG the table does not know about (the record wins over the table); then seal every event still open with file_complete = 0 and cause POWERCUT, and commit the table. Everything is fixed-size: recovery cannot fail for lack of memory.

Files. fmt/ambre_fmt_recovery.c; the proofs live in tests/test_recovery.c and tests/test_explore.c (explore_double_recovery, explore_table_destruction).

    memset(&seal, 0, sizeof(seal));
    seal.event_id        = desc->event_id;
    seal.file_complete   = 0u;
    seal.seal_cause      = (uint8_t)AMBRE_SEAL_POWERCUT;

Prove it. ./build/test_recovery && ./build/test_explore → PASSED: 124 checks, 0 failures and PASSED: 58 checks, 0 failures. Watch event_found_without_table_entry (the EMERG alone registers the event), torn_emerg_is_dropped (a torn record never surfaces), both_tables_destroyed (rebuild by scanning) and recovery_is_idempotent (run twice, same state).

Requirement covered. REP-01..REP-05 I1/I3/I7/I8 — Read the chapter (05-idempotent-recovery.md)

6 · Exhaustive exploration of the cuts

The problem. "Survives a power cut" sounds like an infinite claim, and it is usually argued with a story: we cut the power twenty times and it always came back. Twenty times out of a continuum of instants is not evidence, it is a demo. But the journal performs a finite sequence of operations: cut the power after operation k and you have a finite set of possible disk states.

The idea. Enumerate them all — every prefix of the operation trace, plus the torn-write, lost-cache, bit-flip and wiped-table variants — run the real recovery code on each image and check the invariants I1..I8 against the injected ground truth, never against the recovered data. A recovery that invents state cannot hide, because the expected values come from the input side.

Files. host/explore/ (the checker is host/explore/ambre_invariants.c); the proofs are the campaign itself, run by make explore and make explore-full.

    bool media_fault = (variant_type == AMBRE_VAR_BITFLIP);

    check_i1(rec, report);
    if (!media_fault) {
        check_i2(truth, rec, recovered_disk, prefix, report);
    }

Prove it. make explore → ambre-explore: 10000 states in 29.260s (342 states/s), 0 violations; make explore-full → ambre-explore: 64591 states in 495.263s (130 states/s), 0 violations (measured on 2026-11-11). 64 591 is not a cap that was hit: it is the whole reachable space of the reference scenario, and violations_by_invariant is zero for each of I1..I8.

Requirement covered. ROB-01 spec §7.3 — Read the chapter (06-exhaustive-exploration.md)

The demonstration, in one command

After chapter 4, the whole chain fits in one command: real processes, a real SIGKILL, a real recovery, a real export — on the PC, with the caveats written at the bottom of this page.

bash scripts/demo.sh        # or: make demo
scenariofrontal impact with restraint deployment, 9 000 ms drive, impact at 6 000 ms (host/scenarios/generate.py, preset urban-frontal, seed 1234) — the restraint makes the event locked, so it can never be overwritten
triggerthe drive is replayed through edr-replay → edr-capture → edr-journal; the impact is detected, the Class A snapshot is frozen and written
acquiredthe flush is acknowledged — that instant, and only that instant, is the durability promise (GEL-02)
cutSIGKILL on edr-journal, right after the acquisition
restartthe same disk file: the recovery runs before any new capture (REP-01)
listthe service list shows the recovered event: sealed, locked=yes, complete file=no
exportthe recovered journal image becomes one MCAP file (host/mcap/export_mcap.py)
verifythe official verifier plus the Class A comparison (host/verify/edr_verify.py)
verdictthe script prints DEMO OK — or stops with an explicit error

What to observe. The last two lines of the run are:

    DEMO OK — the event survived a brutal process death, the recovery sealed it,
    the export verified and its class A data equals the injected scenario.

Measured on 2026-11-11 (docs/CAMPAIGN.md §1 and §4): the run took 7.1 s, the SIGKILL landed in the acquired window at +6 033 ms, the recovery returned 1 event sealed locked=yes complete_file=no, the MCAP export exited with rc=0, the official checks were green and the Class A data matched the injected rows 11/11 (alignment 29 ms, worst row slop 4 ms). The demo also prints its own one-shot "acquired in 4.428 ms" under load — that is a single sample, not a campaign figure; the medians are in docs/CAMPAIGN-LATENCY.md.

What this tutorial does not prove

Read this before you quote any number from the codelab. It is the part that makes the rest worth reading.

The PC build proves the logic and the syntax of the QNX glue — not its execution. make qnx-syntax compiles the five *_qnx.c files with -fsyntax-only against stub headers: no typo, no wrong prototype, no wrong struct field. It produces objects only, never links them, and proves nothing about QNX scheduling, drivers, the kernel or the security policy at runtime.

No QNX SDP 8.0 was available on the development machine or the build server, and none could be obtained: no image was built, nothing was booted, no kernel trace was taken, no target latency was measured. Every figure on this page carries backend=posix. The full statement — what each build proves and what it does not — is in docs/QNX-PORT.md.

Killing a process is not a power cut. A SIGKILL does not lose the writes already handed to the host kernel, so the POSIX bench exercises the order and the interruption of writes and the whole recovery path, but not the loss of a volatile cache. That case is covered at level 1 (the cache variant, 21 240 states) and, on the target, by the faulty block server (host/powercut/faulty_block_server.py).

The latency budget is not met by these numbers. PERF-02 (≤ 20 ms trigger → acquired) is not proven: 99.7 % of the measured freeze is NVMe media time on a PC file. PERF-03 (the software share) is met at the median — 10 µs against a 500 µs budget — but PERF-01 is exceeded at the tail (p99 up to 203 ms under disk load). Read docs/CAMPAIGN.md §7 before quoting any of it.

Two pages of this site carry the full picture: the Validation page for the requirement-by-requirement traceability matrix, and docs/QNX-PORT.md for the exact procedure to build and boot the QNX target once an SDP exists — every step of it says what must be observed for it to count as passing, and none of them has been executed here.
