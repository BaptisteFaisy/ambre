The problem

A recorder that has to write at the moment the power dies

Since 6 July 2022 every new vehicle type sold in the European Union must carry an event data recorder. What the device owes the regulator is a kilobyte of pre-crash data — and it owes it in the tens of milliseconds during which the impact may take the 12 V rail down.

Mandatory

Regulation (EU) 2019/2144 makes the EDR compulsory: new vehicle types since 6 July 2022, all new cars and light vans since 7 July 2024; buses and heavy vehicles from 7 January 2026 and 2029. The device cannot be disabled, and it must not record the last four characters of the VIN.

What to record

UN Regulation No. 160 lists the data elements (delta-v, pre-crash speed, belt and brake states, airbag status, ignition cycle, the “complete file recorded” flag), the trigger thresholds (longitudinal delta-v above 8 km/h within 150 ms), the locking rules (above 25 km/h) and the definition of T0.

The hard part is temporal

“The event you must record is the event that destroys your power supply.” A general-purpose stack bounds neither when a task wakes up nor the time spent inside the disk driver, and the Power-Safe file system synchronises a whole volume, not a file.

Ambre is aligned with UN Regulation No. 160. It applies the regulation’s thresholds and records its data elements. It is not “compliant”, not “certified”, not “homologated”, and it is not an airbag ECU. Delegated Regulation (EU) 2022/545 and the 49 CFR Part 563 profile (United States) are referenced in the repository; ISO 26262 certification, mechanical qualification and production-grade crash detection are explicitly out of scope.

Three load-bearing ideas

Save the essential first, keep writing ahead of time, prove it by exhaustion

1 · Save the essential first

The regulatory data set — 5 s before the crash at 2 points per second — weighs about 1 KiB. It leaves for the disk in one single contiguous write: one EMERG record, a 452-byte payload in one 512-byte block with one CRC. The 1.1 MiB of high-resolution Class B data is already on disk from the continuous journal, so nothing bulky stands between the impact and the durable record.

2 · A continuous journal on a raw partition

The journal owns a 48 MiB raw partition with no file system: 24 segments of 2 MiB, 512-byte blocks, each carrying a magic, a version, a sequence number, a session id and a CRC-32C, plus an allocation table in two alternating copies. No metadata journal, no block allocation, no whole-volume sync. At trigger time, only pinning what is already on the disk remains.

3 · Proof by exhaustive exploration

The explorer enumerates power-cut states on a simulated disk: every cut point of the write stream, plus torn writes, cache loss, bit flips, table corruption and cuts nested inside recovery. Each image is re-opened with the real recovery code and checked against eight invariants (I1–I8). The claim becomes a count of explored states with zero violations — reproducible with one command.

How it works

One event, one deadline

From the trigger to the durability point, the path is exactly three steps and nothing else may happen on it. The event is “acquired” only on the flush acknowledgement, never on the submission of the write.

before T0 Continuous journal. Class B samples are written to the raw partition as they come, in blocks flushed every 100 ms. The high-resolution data is already on the disk before anything happens.
T0 Trigger. The capture process runs the UN R160 arithmetic (delta-v above 8 km/h within 150 ms) and keeps the 5 s Class A pre-crash buffer.
t = 0 ① One contiguous write of the EMERG record — the whole Class A snapshot, one 512-byte block, one CRC.
t = 0 ② One allocation-table commit — the copy with the lower generation, generation + 1, then its CRC.
≤ 20 ms ③ One disk flush → ACQUIRED. The event is durable on the flush acknowledgement. 20 ms is the target deadline (PERF-02), not a measurement on the target.
every 10 ms Continuation. While the event runs, one CONT record and one flush every 10 ms.
end + 30 ms Sealing. The SEAL record carries the maximum delta-v and its instant, the restraint deployment times and “complete file = yes”.
later Archive. A low-priority process (priority 8) converts the sealed segments to MCAP on a separate Power-Safe partition — off the critical path, rebuildable at any time from the durable source.

What survives a cut

Specification §4.3 — the risk window is the physical meaning of a 20 ms freeze budget.
Power cut… What survives
before the trigger Nothing to keep: there is no event.
between the trigger and “acquired” Not guaranteed. This is the risk window, and it is exactly the freeze delay.
after “acquired”, before sealing All the pre-crash data, and the crash up to the last flush (at most 10 ms of loss). The event is restored with “complete file = no”.
after sealing Everything, with “complete file = yes”.

Architecture

Five processes, one owner of the medium

QNX scheduling priorities, higher means more urgent. Exactly one process writes to the raw partition, so no writer can interleave with the critical path; the archive and the service tool are strictly lower priority, so an archive write can never delay a freeze.

Specification §4.4 — the five processes of the target runtime.
Process Priority Role May access
edr-capture 60–61 Receives frames, timestamps them, computes the trigger, holds the Class A buffers; on trigger it sends the journal the snapshot. The journal channel only
edr-journal 62 Sole owner of the raw partition. Writes, pins, seals, recovers at start-up; resource manager exposing /dev/edr. The raw partition
edr-archive 8 Converts sealed events to MCAP; manages retention. The archive, the journal read-only
edrctl 10 Service tool: status, list, export, verify. The service interfaces
edr-replay 50 Demonstration producer: replays a scenario file. The input only

The portability layer is the load-bearing wall

target/port/ambre_port.h is one frozen interface — identity, monotonic clock, logging, kernel trace, real-time priority, memory lock, the disk vtable, the message transport, access control, supervision — with two backends: the POSIX backend (PC) is compiled and tested, the QNX 8.0 backend compiles against the stub headers and has never executed. Every process keeps its logic portable and pushes everything OS-specific into a <proc>_qnx.c file — which is why the exhaustive exploration exercises the very code that runs on the target.

Why QNX, in one sentence

On QNX the drivers are ordinary processes, so the journal reaches the disk through a message and the driver runs the write at the caller’s priority (priority inheritance through MsgSend), the journal is a resource manager exposing a typed /dev/edr API, periodic work runs on kernel timers and pulses, the archive sits on the Power-Safe file system, and every deadline claim can be confronted with a kernel trace (tracelogger).

Honesty

What is measured, what is blocked, what failed

This section is the point of the project: the claim “we survive power loss” is only worth something if the boundary of the proof is published with it.

Everything measured was measured on a PC, backend posix. The “raw partition” is a regular file, the flush is fdatasync(), the transport is an AF_UNIX socket, the trace is a text file, and a “cut” is a SIGKILL — not a power cut, and not the loss of a volatile cache. These are claims about logic, not about QNX scheduling, drivers or the kernel.

The target now runs. The QNX SDP 8.0 was installed on the development machine on 2026-11-12, and the five processes compile with the real qcc. They boot in a QNX 8.0 image under QEMU, record a real crash onto a raw partition, and the event survives a real SIGKILL power cut and the reboot — see the target demo page. Since then the /dev/edr resource manager answers its four devctl() from a real client — rendering the same values as the IPC transport — the service access control refuses a producer with EACCES, the archive writes an MCAP on a second medium that is checked outside the guest, and the power-cut campaign judges every cycle (24/24 ok). What remains BLOCKED on target is the kernel trace, the security-policy enforcement by the kernel, the latencies measured as a campaign, and the 2 000-cut sweep; real hardware stays a separate, still-blocked question.

PERF-05 is not met. The requirement is a p99 below 50 µs for the cost of sending one frame; the measured p99 ceiling is 1 ms with no load and 5 ms under disk and memory pressure. Two measured causes: the measurement is a round trip that waits for the acknowledgement, and the quiet drive is not empty — the journal image of that run holds 34 to 102 GAP records, and each gap costs one synchronous journal round trip on the input path. The verdict is published as a failure.

Latency, read with the caveats. The freeze (trigger → acquired) has a median of 3.4–4.3 ms on the PC, but 99.7 % of it is NVMe media time: the software share — the part the code owns — is a median of 10 µs against a 500 µs budget, with a p99 of 56–237 µs depending on the load. PERF-01 is exceeded at the tail (p99 up to 203 ms under disk load), and PERF-04 was measured at the small volume and not met (18 overshoots of the 20 ms deadline over 1 007 cycles). The 20 ms deadline on the reference hardware remains a target.

Two bench verdicts are published unresolved rather than hidden: the 200-cut run keeps one check_failed (Class A fidelity on one cycle) and two findings on the gaps channel; the 500-cut close-out keeps two inconsistent_state (I7) whose events carry seal_cause=NORMAL — the seal had reached the disk before the kill landed, which POSIX allows. A campaign whose only blemish is hidden is worth nothing.

Wording. Ambre is aligned with UN Regulation No. 160. It is not compliant, not certified and not homologated. The 01 series of amendments to R160 — the one the EU references — could not be consulted and must be re-read before submission.

Getting started

Five commands, on any Linux machine

No dependency beyond libc and a C compiler: the portable core is C11, the archive is C++17, the host tools are Python 3. Clone the repository and run:

make                  # library, unit tests and tools (gcc, C11, -Werror)
make test             # every unit and integration suite; exit code = failures
make explore          # 10 000 cut states, all write variants
make verify           # export one event and check it against its scenario
bash scripts/demo.sh  # end-to-end: replay → capture → journal → SIGKILL →
                      # recovery → MCAP export → official verifier
make crosscheck       # C trigger vs the independent Python twin (DEC-12)

Nothing above needs a QNX installation. To cross-compile the target layer, obtain the QNX SDP 8.0 and run make qnx-syntax (a syntax-only compile of the five glue files against the stub headers) and make image-check (eleven static checks on the image fragments and the security policy); the boot procedure itself is written down in docs/QNX-PORT.md and has never been executed.
