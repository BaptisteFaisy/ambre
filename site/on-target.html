On the target — QNX 8.0, emulated on QEMU, on this machine

The black box really survives the crash

The five processes are compiled with the real QNX SDP 8.0 toolchain (qcc, gcc_ntox86_64), boot in a QNX 8.0 image under QEMU, and record a real crash onto a raw partition. Then the host cuts the power — a SIGKILL on QEMU, the cache is gone — and after the reboot the journal recovers what was left on the platter.

What was proven, and what that means

The project runs on the target operating system: the SDP 8.0 is installed, the image boots, and the chain executes in the guest. What follows is what that run demonstrates — and, below, what it still does not.

What the target run demonstrates, item by item.
ClaimProven on QNX 8.0 (QEMU)
The five processes build for the targetyes — make qnx links them with qcc, -Werror, against the real headers
The journal opens a raw partition and runs recoveryyes — /dev/hd0t177, no file system (STO-01), recovery done … self-test OK
capture → trigger → journal → acquiredyes — one restraint trigger and seven delta-v triggers during the impact pulse, all acquired
A flush from QNX reaches the virtual diskyes — the journal flushes the raw partition (fsync), and the SIGKILL loses only what was not flushed
A real power cutyes — kill -9 on QEMU: the guest's volatile cache is gone
The event survives the rebootyes — recovery (REP-01) reads the table, the events come back sealed and locked
Frame send cost on target (essay E4 / PERF-05)measured, not met — mean ~636 µs, p99 over the 50 µs requirement (QEMU timing, see below)
The resource manager /dev/edr answers devctl()yes — a real client (devctl_probe) drives STATUS, LIST, EXPORT and AUTOTEST, and renders the same values as the IPC transport on the same journal. The codes are QNX-encoded: the bare project numbers encoded a size of 0, and the kernel copied nothing back
The service access control on target (SEC-01)yes — the service peer (gid 4) is served, a producer (gid 3) gets EACCES: refused by the kernel credentials, not by a unit test
The archive on a second medium (STO-07)yes — a FAT32 partition mounted on /arch, edr-archive writes the MCAP there, and the file is read back outside the guest and checked by the project's own verifier (10 of 11 checks)
Real power cuts, judged one by oneyes — the level-2 campaign drives the guest, cuts the power, reboots and judges what the journal renders: 24/24 cycles ok at cut offsets 0–120 ms after the acquisition, 8.04 s per cycle

QEMU is emulation, not hardware. The operating system is really QNX 8.0, and the cut is a real power cut at the process level — but the machine is qemu-system-x86_64, not an ECU: the latencies printed here are emulator numbers and must not be read as target performance. Real hardware (a Raspberry Pi 5, SD then NVMe) is still BLOCKED.

Still not demonstrated on target, and still labelled BLOCKED in the repository: the application of the security policy by the kernel (the policy now compiles — make secpol, no warning — but pushing it into this image breaks the boot whatever rules the launcher type is given; the remedy is to boot the base through slm and type every service), the kernel trace and the priorities it would show, the latencies measured as a campaign on the target, the supervision by HAM, the product image assembled by mkqnximage, and the 2000-cut sweep and the volatile-cache variant.

The full machine-readable artifacts — the demo script, the boot image, the console bridge and the transcript — are in the repository: scripts/qnx-demo.sh · image/qemu.build · docs/QNX-DEMO.md · docs/QNX-DEMO-TRANSCRIPT.md.

Reproduce it

source ~/qnx800/qnxsdp-env.sh        # the SDP 8.0 installed on the development machine
make qnx                             # the five binaries, real qcc, -Werror
# the boot image (kernel, ksh, the block stack, the five processes, the demo):
scripts/qnx-vitrine.sh build         # mkifs image/vitrine.build → build/qnx-vitrine/ifs.bin
scripts/qnx-vitrine.sh run           # the loop: boot → crash → SIGKILL → reboot → verdict

The bench is scripts/qnx-vitrine.sh (build + the loop) with the console helpers qnx_console.py and qnx_bridge.py. The journal disk is a 64 MiB raw file with one partition of type 177 and cache=none, so a flush reaches the host file and a kill is an honest power cut. The live guest runs on the r630 as two systemd user units — ambre-vitrine-qemu.service (the loop) and ambre-vitrine-web.service (the HTTP vitrine) — and the funnel exposes it under /ambre.
