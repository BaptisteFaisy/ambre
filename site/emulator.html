Live — a QNX 8.0 guest under QEMU, on the r630

The emulator, live

This is not a recording and not a simulation: it is a QNX 8.0 guest, booted from an image built with the real SDP, running the five Ambre processes on a raw partition. The frame below is its VGA screen, captured through the QEMU monitor; the panel on the right is its serial console. The crash is driven inside the guest, and the power cut is a real SIGKILL on QEMU — the volatile cache goes with it. Then the guest reboots on the same disk and recovers what was left on the platter.

Watch the guest The transcript and the proof

The guest, right now

The loop never stops: the guest boots, drives the crash, the host cuts the power, the guest reboots and recovers — then it starts again. The buttons type into the guest: they are injected as real keystrokes (QEMU sendkey), so the answer appears on its screen, not here.

The real figures, measured on the target

The guest publishes its own measurements (edrctl --json run inside the guest, on its serial console) and the page reads them from there: its state every 2 s, its events at the moment they happen. These are the target's numbers, not the PC backend's — and the console panel below shows the guest's own words, the machine markers aside.

The guest may be asleep. The r630 hosts several QNX guests, so this one is stopped after a few minutes without a visitor and started again on the next request — the boot takes about a minute. The screen then shows the guest booting from scratch. It is the same guest, the same image and the same disk.

Two benches, one screen. The primary bench is the r630. If it is unreachable, the page switches once to the identical bench running on the development PC and names the bench it is showing in the status line — it never switches quietly, and it never pretends to be live when it is not.

What the loop does, inside the guest

1

edr-journal opens the raw partition /dev/hd0t177 — no file system on it — and runs the recovery before anything else

the recorder owns the medium, byte for byte

2

edr-capture listens, edr-replay replays the scenario: 4 s of driving, frontal impact at 2.5 s

the trigger fires inside the guest, on the guest's own clock

3

the impact is acquired: event 1 sealed locked=yes complete_file=yes, then the host cuts the power

kill -9 on QEMU — the 12 V rail and the volatile cache are gone

4

the guest reboots on the same disk: the recovery scans it and the event comes back sealed and locked

the event survived the power cut — the console says so, live

What this page is, exactly

Every claim on this page, and where it comes from.
What you seeWhere it comes from
The screenscreendump on the QEMU monitor of the running guest — the VGA framebuffer, not a rendering
The consolethe guest's serial port, byte for byte
The keyssendkey on the QEMU monitor: real keystrokes in the guest's VGA keyboard
The crashdriven by edr-replay inside the guest, from the scenario file that is in its image
The power cuta SIGKILL on QEMU from the host: the guest's cache is gone
The recoverythe guest's own recovery code, on the same disk, after the reboot

QEMU is emulation, not hardware. The operating system is really QNX 8.0 and the cut is a real process-level cut, but the machine is qemu-system-x86_64, not an ECU: the latencies the guest prints are emulator numbers and must not be read as target performance. Real hardware (a Raspberry Pi 5, SD then NVMe) is still BLOCKED.

There is a second, different tool on this site: the explorer runs the same recovery code compiled to WebAssembly inside your browser, on the PC backend, and lets you cut the 12 V rail anywhere in the write stream. It is a tool, not the target — this page is the target.
